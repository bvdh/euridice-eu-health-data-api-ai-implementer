# FHIR-56695: : Document Exchange needs a better use of date and time related search parameters

## Description

Document Exchange needs a better use of date and time related search parameters

The support of MHD as proposed makes sense, however:

	- The document search proposed in the use of the MHD Document Reference resource is too primitive as it only relies on two mandatory parameters: documentType limited to the EHDS Data Category (encoded by a value set of 6 arbitrarily picked LOINC Code) and document contentType (MIME Type).

	- The time stamps associated with the documents exchanged or searched need to be made more explicit and clearer with their semantics. The design of MHD supports for solid reasons for four types of time stamps:

 - Document Creation Time. The time the document is created according to the format defined by the corresponding FHIR IG.

 - Document publishing time. This ensures that incremental queries can be performed (querying for any documents published after time hh:mm:ss, when this time is the time of the last query).

 - Period. Includes a required service StartTime and an optional service End Time.  This ensures the filtering of documents by queries based on care provision time interval.

 - LastUpdated The attribute «lastUpdated» allows to easily search for modified documents since a point in time.

 

Proposed resolution :

It is proposed to include the above four time stamps:

Update : Search Strategy:

	- Document Creation Time{*}. The time the document is created according to the format defined by the corresponding FHIR IG.

	- Document publishing time{*}. This attribute is part of the submission set.  This ensures that incremental queries can be performed (querying for any documents published after time hh:mm:ss, when this time is the time of the last query).

	- Period{*}. Includes a required service StartTime and an optional service End Time.  This ensures the filtering of documents by queries based on care provision time interval.

	- LastUpdated* The attribute «lastUpdated» allows to easily search for modified documents since a point in time

 

All above search parameters shall be required to support server side filtering of matching Document References (shown by *).  A subset of these search parameters shall be supported for search query request (server-side filtering).  All shall be returned by the server whether they were or not included in a query instance (except for the Period End-Time, only if present).

### Andries Hamster — 2026-05-28

[charles@interopehealth.com](https://jira.hl7.org/secure/ViewProfile.jspa?name=charles%40interopehealth.com) can you elaborate on the difference between creation and publication time? If I understand your comments correctly you like to differentiate between the time a documentResource was created and the time that documentResource was made public (i.e. published). Correct?

My understanding is that the:

	- documentReference.date = the creation time of a reference to a document. The document itself may have a different date as a system could create a docRef for a document that was made in the past.

	- documentReference.meta.lastUpdateTime is reflects when the docRef was updated but not the document it references.

So when an document is updated both the creation time and the lastUpdateTime likely change. If only document metadata is updated the docRef is updated but not its creation time. For example, a code/label that is added to a document's metadata after initial publication may lead to an update to the docRef.

Period is an attribute that reflects a time period of some contextual condition or situation that lead to the creation/publication of the document referenced by the docRef. For example, a discharge summary documents an episode of care given to a patient. Or a radiology reports documents a finding for a diagnostic procedure/service request that was carried out. 

Although it is possible to use a submission time stamp as a publication time stamp I am not sure why this is needed in the EU API context. The original use of a submission set was to allow for grouping the publication of one or more documents. For example group a manifest and a report document that are results of the same diagnostic imaging event. However, that is also possible by using the 'relatesTo' attribute.
