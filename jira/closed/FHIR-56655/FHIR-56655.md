# FHIR-56655: Patient.$match design rationale: claim that "richer context" (aliases, prior identifiers, phonetic matching) is unique to $match is not accurate — applies to Patient.Search too

## Description

The Patient Match design rationale reads:

Patient.$match moves resolution to the server, which has richer context (aliases, prior identifiers, phonetic matching).

The claim that this server-side context is unique to $match is inaccurate. Both Patient.Search and Patient.$match execute server-side and access the same demographic context. The substantive difference is safety semantics: $match returns scored candidates with explicit match-grade signaling, letting the consumer apply onlyCertainMatch and similar guardrails. State the real differentiation rather than a server-context advantage that doesn't exist.

If Patient.Search is removed in favor of Patient.$match (per the patient matching ticket #11), this rationale becomes moot — the comparison disappears with the other transaction.

Proposed resolution:

Rewrite the design rationale to describe $match's actual differentiation from Patient.Search:

	- Returns scored / graded candidates with search.score and search.extension[match-grade] (FHIR core).

	- Supports onlyCertainMatch to suppress lower-confidence candidates.

	- Encapsulates server-defined matching logic (probabilistic, deterministic, MPI-backed) without leaking that logic to the consumer.

Reporter(s): Aaron Mahr, Epic

## Resolution

- Status: Applied
- Resolution: Persuasive with Modification
- Resolution Vote: Mattias Colliander / Charles Parisot: 6-0-1
- Vote Date: 2026-08-12

After a discussion on the API call the agreement was to keep the status quo, meaning that patient search is required and $match optional. The differentiation will be improved, the proposed arguments will be incorporated. Exception: “Encapsulates server-defined matching logic (probabilistic, deterministic, MPI-backed) without leaking that logic to the consumer” will not be taken over, since the same is true for the business logic for Patient Search.
