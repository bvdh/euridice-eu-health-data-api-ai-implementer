# FHIR-56652: FHIR documents and resources guidance — make explicit that documents are targeted, with resource access for the long tail

## Description

A primary value of FHIR was that it introduced REST among other "Web 2.0" IT data exchange techniques to health IT, adding to existing paradigms such as operations/function-driven APIs (i.e. SOAP), documents and messaging. Document exchange is commonly characterized as use-case-specific summary exchange. Resource access naturally serves as a release valve enabling summaries to remain small, and interop to address unplanned-for use-cases. Documents should be targeted — active, or in-progress and only obviously relevant clinical content — relying upon resource access to solve the other 20% (or even 30–40%) of needs.

The IG today doesn't make this division explicit on fhir-documents-vs-resources.html or in the priority-area pages. Adding the framing would help implementers see the two patterns as complementary tools for different jobs, and would push them toward resource access for content that doesn't belong in the targeted summary Document.

Related to but distinct from the on-demand-assembly change request (which addresses how documents are built — assembled vs. persisted); this ticket addresses what content belongs in them.
