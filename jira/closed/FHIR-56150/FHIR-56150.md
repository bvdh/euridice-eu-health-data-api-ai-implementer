# FHIR-56150: Actors ignore push of information

## Description

The interpretation of "be able to receive" is too narrow, when it is reducted to the scenario "Consumer: Initiate queries and receive responses."

In the EHDS regulation, Article 5 gives natural persons the right to insert information in their own EHR. This is clearly a requirement for an EHR to "be able to receive" content that is has not requested. That is, to respond to a PUSH request by a third party rather than processing an answer to a request the EHR initiated.

Same applies (perhas not as clearly) to Article 6 Right of natural persons to rectification.

The same is again more clearly a requirement in Article 7 Right to data portability for natural persons.

All of the four mentioned data portability use cases are initiated by the patient, and therefore require the EHR to "be able to receive" content from a request it has not initiated.

Further, second part of Article 48 clearly indicates a use case where data is transmitted from a wellness application to an EHR system. Remote monitoring is a clear use case for this, and already prevalent. It is clear that the remote monitoring use case is something the EHDS API specification needs to address.

 

The rationale justifying the way the actors are specified in the specification is far from complete.

The "clinical workflow fit" assumes a single use case, a patient arriving to a new care setting. There are many more scenarios in which a patient may want to transmit their data from a provider to another. The patient may, for instance, already be receiving care from multiple providers, and those providers may not be exchanging data between themselves. A patient may assume an active role here, triggering the transfer of a piece of health information from a provider to another.

On "MyHealth@EU alignment", the guide explains that EU Cross-border services are primarily modeled as query-based exchanges. This may reflect the scenario today, but does not tell much about how things will work when the EHDS is operational.

On "data availability", the guide explains that healthcare is 24/7. An API endpoint can serve requests at any time, ensuring data is accessible when needed for care. With a push architecture, data availability depends on the receiver being online and the sender initiating data transmission. This is contradictory. If healthcare is 24/7 and an API endpoint can serve requests at any time, why could the API endpoint not be able to process incoming PUSH requests at any time?

 

Either the entire API implementation guide needs to be re-specified from scratch, or there needs to be language explaining that this is a first version that tackles pull based architecture, and a upcoming version in the future will cater for PUSH based use cases.

PUSH based use cases do exist! We do need to cater for them.
