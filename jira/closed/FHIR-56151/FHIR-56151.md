# FHIR-56151: API requirements should be more constrained, need to be forward-looking

## Description

All of the requirements cater only for a really narrow subset of use cases. The implementation guide needs to be written in a way that allows for future evolvement, at least for foreseeable parts.

 

For instance, `api-consumer-authObtainToken` is described to be backed by technical specifications SMART Backend client credentials grant and IHE IUA.

First, it would be nice if the API specification could already make a selection and specify one of these, and not both. It would most likely to be better for interoperability, right?

Second, the API should be aware of use cases it does not yet describe. Remote patient monitoring through a wellness app is a prime example. The auth token retrieval would in this case most likely be defined in International Patient Access (IPA) specification, right?

It would be better to name the requirement as `api-consumer-backendObtainAuthToken` or something similar, to indicate that this use case concerns EHR-to-EHR backend communication (through documents?) and not wellness app to EHR communication, which is essential but not yet part of this API specification.
