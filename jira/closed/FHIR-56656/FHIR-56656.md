# FHIR-56656: Patient.Search: clarify expected server behavior when client has no identifier and server doesn't support $match

## Description

The IG requires the identifier parameter on Patient.Search (ITI-78) and lists Patient.$match as MAY. How should a server handle a Patient.Search without an identifier when it doesn't support Patient.$match?

For a client without a patient identifier calling a server that doesn't expose $match, one of the following must hold:

1. Patient.$match is functionally required server-side (so the client uses $match).

2. The client must always have an identifier (excluded by precondition).

3. Servers can treat identifier as optional on Patient.Search with fallback semantics.

Proposed resolution:

Pick one and document it. Recommended: require Patient.$match server-side (aligning with the broader move toward $match as primary — see the patient matching ticket) and call out explicitly that systems supporting only Patient.Search leave the no-identifier scenario unsupported.

## Resolution

- Status: Resolved - No Change
- Resolution: Not Persuasive
- Resolution Vote: Mattias Colliander / Charles Parisot: 6-0-1
- Vote Date: 2026-08-12

After a discussion on the API call the agreement was to keep the status quo, meaning that patient search is required and $match optional. Providing identifier and/or demographics can be accomplished with both patient search and $match transactions (reminder: SHALL support a certain search parameter means that a system has to able to process it and not that is has to be present in every query). What to use depends on the governance for the identifier and the “set of agreed identification attributes” which is varying between the member states.
