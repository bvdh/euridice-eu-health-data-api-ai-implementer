# FHIR-56304: Make Chained Identifier Search a formal option

## Description

Move section 3.3.6.1 (Chained Identifier Search) from "3.3.6 Examples" to "3.3.3 Transaction Options". It is a very important option for Sweden. Moving it into the transactions options section will allow procuring organizations and member states to make it a referable requirement. Having it in the Examples section doesn't make sense to us. Any arbitrary part of the standard is by definition a valid none formal example. We don't se any value of having it in the current location, but appreciate that it has been mentioned though, as it made it a low effort task to add this change request.

## Resolution

- Status: Applied
- Resolution: Persuasive with Modification
- Resolution Vote: Mattias Colliander / Charles Parisot: 6-0-1
- Vote Date: 2026-08-12

The Chaining part will be moved from the example section as requested, however it will be moved from the Patient Lookup page to the Document Exchange page since its actual purpose is to search for documents for a certain patient and not for a patient itself. Furthermore, it will be mentioned that chaining might not be possible in every constellation (e.g. when logical references are used on the document metadata).

### JoshPriebe — 2026-04-22

Johan - Swedish use cases:

	- In a federated Architecture, the resource providers are many individual systems. It does not make sense when a record locater system exists, to identify a patient with each resource provider individually. Effectively, patient matching is externalized to the national infrastructure (similar to auth).

 - Relies on the records location system being always up to date - this is required by law in Sweden. You must always keep national EMPI up to date.

 - How are Emergency situations handled? Foreign patients? They get temporary ID's, for example when foreign patients show up.

 - No national handling for foreign patients today, though EHDS will bring this.

I want to hear from other use cases here as well.
