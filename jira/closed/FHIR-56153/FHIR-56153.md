# FHIR-56153: Resource access is unnecessarily constrained

## Description

Limiting resource access to read only feels unnecessary and seems like a bad choice.

There are use cases in EHDS that clearly demand creation of data. Article 5 gives natural people several rights to push their data into EHR systems. Article 48 indicates how wellness apps insert data into EHR systems.

All these use cases seem to be more appropriately served by creating resources rather than documents.

If the EHDS API specification only defines a write capability for document based workflows and explicitly denies creation of resources, we're bound to see very silly implementations with, for instance with patient remote monitoring, each individual resource being sent by the wellness application within a document. This makes absolutely no sense.

There is a note about Resource Publisher, and an entire section (3.6) for Resource Exchange. However, I think the reasoning is poorly justified.

Remote monitoring as a use case has been successfully implemented with HL7 FHIR and by numerous EHR systems. There should be ample evidence that it works and can be implemented. There is no need to leave it out from the API specification.

Even worse is an API specification that expicitly prevents remote monitoring being implemented with a resource based workflow and forces implementers to do that with documents.

Section 3.6.2 of the implementation guide lists three challenges. All can be easily resolved.

1) Resolving references. As mentioned, there are many existing use cases for remote monitoring and beyond, implemented with HL7 FHIR and IPA, proving that this is not a problem.

2) Unsolicited Data. Writing an API specification that includes information on which API details should be used when receiving data does not mean that the API specification needs to account for this kind of challenges. Surely there are similar challenges with receiving documents. And again, existing use cases for patient remote monitoring demonstrate that this is not an issue and can be implemented.

3) Reconciliation. Again, there is no such a big difference between FHIR resources and FHIR resources bundled into a dummy document structure. It can be easily expressed in this API specification that reconciliation is left to servers and use-case-specific implementation guides to resolve.

The API specification should just adopt the IPA specification as a whole for resource exchange, including write capabilities. Of course this would not mandate each EHR on the market to support each resource type, or to support write capabilities at all. But the API specification should express that when resources are exchanged, IPA should be used. And not exclude resource creation.

PUSH based and resource based workflows exist and are required and need to be supported by this specification - or at the very least the next version of this specification.
