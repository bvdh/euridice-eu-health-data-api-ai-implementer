# FHIR-56388: Security and Authorization

## Description

The API specification introduces a client private key signed JWT as the client authentication mechanism for EHR-to-EHR exchanges. This mechanism authenticates the client at token issuance, but the resulting token remains a bearer credential: if intercepted in transit, it is immediately exploitable without any further proof of identity. In a channel carrying health data, this residual risk warrants an explicit technical response in the specification. RFC 8705 and mTLS provides that additional security level by cryptographically binding the token to the issuing client: even if intercepted, the token becomes unusable without the corresponding certificate.

Proposed resolution :

This proposed approach does not challenge the existing private_key_JWT mechanism but offers implementers a higher-assurance alternative when their infrastructure context or national regulatory obligations justify it. It is therefore proposed to introduce an explicit reference to RFC 8705 and mTLS in the specification as a supported option, on equal footing with private_key_jwt. Leaving this choice to the implementer respects the diversity of EHR architectures across Member States, while giving those seeking a higher assurance level the technical means to achieve it.
