# FHIR-56369: Clarify IUA vs SMART actor usage

## Description

The guide appears to introduce additional requirements for the actor labeled as an IUA Authorization Client.

SMART is the "reference" for this part when conflicts arise.

It is unclear whether an actor that includes such additional constraints can still be considered compliant with the standard definition of an IUA Authorization Client.

Clarify the actor definition by defining a separate, explicitly named actor (e.g., an ad hoc or derived actor).

## Resolution

- Status: Triaged
- Resolution: Persuasive

This ticket is addressed by the actor and authorization clarifications proposed in [PR #99](#99)([https://github.com/euridice-org/eu-health-data-api/pull/99](https://github.com/euridice-org/eu-health-data-api/pull/99)). The changes distinguish the generic Health Data API Authorization Client from the separate protocol-specific IHE IUA Authorization Client and SMART actors. For each Resource Server endpoint, the applicable environment selects one protocol profile. Accordingly, IUA and SMART requirements are not combined on the same endpoint and cannot conflict there; the ticket's concern about which actor definition governs in a conflict is addressed by selecting the applicable protocol-specific actor. The generic role does not itself claim conformance to either protocol, and the Authorization guidance distinguishes core IUA requirements from applicable MHD integration and additional recommendations. No third derived IUA actor or universal SMART-over-IUA precedence rule is needed: the generic role and the protocol actors are distinct, and each endpoint selects its protocol.
