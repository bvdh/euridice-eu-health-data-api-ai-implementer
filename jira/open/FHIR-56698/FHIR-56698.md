# FHIR-56698: SMART Authorization

## Description

What is the rationale behind adopting SMART Backend Services for authorization (and the required binding with an IUA Authorization Server)? Moreover, the resource-based access scopes defined in SMART (c.f. sec. 3.5.8 Resource Access) are rather to be defined via regulatory groupings in a national infrastructure (and thus probably more coarse-grained).

Proposed resolution: References to RFC6749, RFC8414 etc. might satisfy the general requirement for authorization.

## Resolution

- Status: Triaged
- Resolution: Not Persuasive with Modification

The ticket is addressed with modification by clarifying when the EU Health Data API recommends IHE IUA for preconfigured national system-to-system endpoints, when SMART Backend Services may be used, and how these profiles and their scopes are selected for each endpoint. Interactive Wellness Application access continues to use SMART App Launch. IUA MHD transaction scopes apply only to the relevant supported transactions and grouped actors, while SMART endpoints use the applicable SMART FHIR resource scopes. These changes are in [PR #99 — Eu health data api ballot recon authorization](#99 — Eu health data api ballot recon authorization)([https://github.com/euridice-org/eu-health-data-api/pull/99](https://github.com/euridice-org/eu-health-data-api/pull/99)). The ticket's suggested replacement with generic OAuth references and a general national coarse-grained scope vocabulary is not adopted by this change
