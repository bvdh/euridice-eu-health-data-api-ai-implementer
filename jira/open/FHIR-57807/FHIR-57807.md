# FHIR-57807: Address Terminology Handling

## Description

As there most likely it will not be possible to mandate harmonized terminologies and value sets across Europe the Europe Commission is expected to make a defintion for the cross-border communication to which the member states need to map.

Besides the general terminology drift challenge which is pointed out in this post [https://medvertical.com/blog/terminology-drift-silent-killer-fhir-data-quality](https://eur04.safelinks.protection.outlook.com/?url=https%3A%2F%2Fmedvertical.com%2Fblog%2Fterminology-drift-silent-killer-fhir-data-quality&data=05%7C02%7Candreas.klingler%40siemens-healthineers.com%7Ce90a08527b3f464aba6608ded1dec552%7C5dbf1add202a4b8d815bbf0fb024e033%7C0%7C0%7C639178951901686591%7CUnknown%7CTWFpbGZsb3d8eyJFbXB0eU1hcGkiOnRydWUsIlYiOiIwLjAuMDAwMCIsIlAiOiJXaW4zMiIsIkFOIjoiTWFpbCIsIldUIjoyfQ%3D%3D%7C0%7C%7C%7C&sdata=PWVZQ%2FWfcpev%2FnpRv7PO53zZlEHIRh2PS7n7ORz1A40%3D&reserved=0) this introduces additional terminology management and mapping use cases which need to be addressed by member states and which have potentially impact on the harmonized interopereability component. 

Widening the scope of the EU Health Data API specification is advised. incl. pointing to the  ITI Sharing Valuesets, Codes, and Maps (SVCM) Profile [https://profiles.ihe.net/ITI/SVCM/index.html](https://profiles.ihe.net/ITI/SVCM/index.html) in trial implementation, which can help with that. It is a profile on the FHIR terminology services and was tested at each EU Connectathon since 2021.

And potentially triggering the creation of addtional IHE Profiles in collaboration with IHE ITI through the IHE PRISM EHDS.

Initial (Copilot) assessment of ITI SVCM Profile fit:

👉 SVCM adds situational value — but is not essential in a pure FHIR-first EHDS architecture

	- ✅ Useful for: governance, conformance testing, and IHE-aligned ecosystems

	- ⚠️ Limited added value if you already:

	- use FHIR-native terminology services

	- rely on HL7 IGs + national governance (e.g., EHDS frameworks) (ak: Well, copilot did not get that we aim to base the EHDS frameworks on IHE Profiles for adding the IHE values listed below, and more).

👉 In many modern deployments:

FHIR Terminology Services alone are sufficient — SVCM becomes optional.

🧩 What SVCM actually adds (beyond FHIR)

SVCM is intentionally lightweight. It:

	- Reuses FHIR terminology resources

	- ValueSet, CodeSystem, ConceptMap [[fhir.hl7.org]](https://fhir.hl7.org/fhir/terminology-module.html)

	- Adds:

	- IHE actors + transactions

	- conformance constraints

	- testability (Connectathon readiness)

👉 That means its value is not technical capability, but operational alignment.  (Ak: this is actually the important point!)

✅ Value areas where SVCM matters
1. IHE-style interoperability contracts

If your ecosystem depends on IHE-style procurement or validation:

	- SVCM provides:

	- Clear actor model (Terminology Repository / Consumer)

	- Defined interaction patterns

	- A testable conformance target

👉 This aligns with IHE’s core role:

	- providing “a common language for purchasers and vendors” [[ihe.net]](https://www.ihe.net/resources/profiles/)

✅ Value: HIGH in:

	- multi-vendor hospital ecosystems

	- procurement-heavy environments

	- Connectathon-driven validation

2. Bridging legacy IHE ecosystems (XDS, SVS)

In real-world infrastructures:

	- Many systems still use:

	- XDS metadata with controlled vocabularies

	- SVS-based value set distribution

SVCM helps:

	- transition from SVS → FHIR

	- unify terminology handling across old/new stacks

✅ Value: HIGH for:

	- migration programs

	- hybrid architectures (XDS + FHIR) (ak: some MS have that!9

3. IHE governance alignment across domains

IHE profiles (Radiology, Lab, Pharmacy):

	- depend heavily on:

	- value set consistency

	- terminology bindings

SVCM offers:

	- a cross-domain consistent mechanism

✅ Value: MEDIUM–HIGH when:

	- you use multiple IHE profiles together

	- you want uniform terminology infrastructure

4. Testing & Connectathon participation

A key differentiator:

	- Pure FHIR usage → often loosely constrained

	- SVCM → formally testable profile

This enables:

	- repeatable vendor validation

	- reduced ambiguity

✅ Value: HIGH if:

	- you rely on IHE Connectathons

	- you need formal certification-like assurance

❌ Where SVCM adds little or no value
1. FHIR-first EHDS architecture (core case)

EHDS direction (implicitly):

	- API-based exchange

	- FHIR-based semantic interoperability

	- strong national / EU governance of value sets

FHIR already provides:

	- full terminology service capability:

	- $expand

	- $validate-code

	- $translate [[fhir.hl7.org]](https://fhir.hl7.org/fhir/terminology-module.html)

👉 SVCM does not add new functionality

⚠️ Result:

	- It can feel like a redundant abstraction layer

✅ Value: LOW in:

	- greenfield EHDS platforms

	- centralized terminology services

	- API-driven architectures

2. HL7 IG–driven ecosystems

Modern FHIR ecosystems use:

	- Implementation Guides (IGs)

	- CapabilityStatements

	- National profiles (e.g., Gematik, NHS, TEFCA-like frameworks) (ak: Meaning: they all reinvent the wheel. Which is one of the problems we want to address. Also gematik is interested in this.)

These already define:

	- required operations

	- bindings

	- constraints

👉 SVCM duplicates some of this governance role

✅ Value: LOW–MEDIUM, depending on overlap

3. Cloud-native / platform architectures

Typical setup:

	- central terminology server (Ontoserver, Snowstorm, etc.)

	- direct FHIR API usage

No need for:

	- intermediate IHE abstraction

	- additional actors

✅ Value: LOW

🧩 Implication for EHDS

EHDS will likely favor:

	- ✅ FHIR-native terminology services

	- ✅ Strong governance of value sets

	- ❌ Minimal reliance on IHE-specific APIs (ak: EURIDICE is trying to change that. 😊 )

👉 Therefore:

SVCM is complementary, not foundational

🚧 Key gap (where SVCM still underdelivers)

From an advanced interoperability perspective:

SVCM does NOT sufficiently address:

	- semantic governance workflows

	- version lifecycle management across jurisdictions

	- terminology federation (multi-authority)

	- binding enforcement across distributed systems

👉 These are core EHDS challenges (ak: I agree. Probably some things the EURIDICE API WG/ITI should pick up through IHE PRIM EHDS?)
