# FHIR-59602: Delegated Access Option: support end-to-end encrypted EHR systems

## Description

We are developing Cliente2, a records and billing application for psychotherapy practices in Austria and Germany, offered as a service (EHDS Art. 26(2)). For data privacy reasons it is end-to-end encrypted (i.e. zero-knowledge): patient records are encrypted and signed on the practitioner's devices, and our servers store and synchronise them only as ciphertext. No server-side component holds a key that decrypts records; we as the vendor cannot read them. For psychotherapy data we consider this an important safeguard (data protection by design, GDPR Art. 25).

Problem

Xt-EHR D5.1 (section 3.1.4) interprets Annex II §2.1 as a query-based architecture: the EHR system acts as Access Provider and answers ITI-67/ITI-68 and IPA queries at any time. For an end-to-end encrypted system, answering a query while no practitioner device is online requires a server-side component that can decrypt the record, assemble the "Patient Summary" and decide on its release. That would add a plaintext store of every client's diagnoses and medication on the vendor's servers, which is the exposure the architecture is designed to avoid.

The Delegated Access Option fits this case: the practitioner's device builds the EEHRxF document and publishes it with ITI-105 to an Access Provider, which serves the queries. Plaintext then leaves the practice only towards the infrastructure meant to receive it. The rationale given in the IG ("systems not suited for 24/7 API hosting", e.g. an iPad clinician app) already covers part of this. End-to-end encrypted systems are a second, distinct reason: they could host an API, but by design cannot serve plaintext from a server.

Requested changes

1. Keep the Delegated Access Option, and state normatively that an EHR system implementing Document Publisher (ITI-105) towards an Access Provider satisfies Annex II §2.1 for the content it publishes. 

2. Add end-to-end encrypted EHR systems to the rationale of the option, next to systems not suited for 24/7 API hosting.

3. Give guidance for publisher-only systems on when to publish and how to supersede earlier documents. D5.1 notes that a Patient Summary has no natural push trigger; one approach is to publish a new version whenever summary-relevant data changes, replacing the previous one (DocumentReference.relatesTo, code "replaces").

4. Clarify the federated pattern (Member State Architectures, Pattern 2): where no national or regional repository accepts publication, may a publisher-only EHR system publish to another Access Provider chosen by the healthcare provider, and what does the IG expect in that case?

Question

D5.1 places a generic push architecture out of scope and recommends that central repositories query EHR systems instead. How will the Delegated Access Option be carried into the input for the Art. 36 implementing act, so that it does not remain an option of this IG alone?

Related

The receive side (Annex II §2.2) raises a separate question for browser-based EHR clients: authorisation without a server-held client secret, and CORS on Access Providers. I plan to raise it in a separate ticket.
