# FHIR-56973: Document Publication – Adding ITI-106 as a publishing option

## Description

Summary: The EU Health Data API IG 1.0.0-ballot currently specifies ITI-105 (Simplified Publish) as the publication transaction but does not include ITI-106 (Generate Metadata). We strongly recommend adding ITI-106 as a REQUIRED transaction for the Document Access Provider actor.

Comment:

We are implementing software that acts as an EEHRxF Document Publisher for AI-generated imaging reports conforming to the HL7 EU Imaging Report IG (BundleReportEuImaging, Level 4.2). Based on our implementation experience, we request the inclusion of IHE MHD ITI-106 (Generate Metadata) in the EU Health Data API IG for the following reasons:

	- Reduced client complexity and metadata duplication: With ITI-105, the Document Publisher must manually assemble a DocumentReference resource — duplicating type, subject, dates, and status information that is already present in the Bundle's Composition and DiagnosticReport resources. ITI-106 eliminates this duplication by having the Document Access Provider derive the metadata directly from the submitted Bundle. This follows the DRY principle and reduces the risk of inconsistencies between the DocumentReference and the actual document content.

	- Lower barrier to adoption for clinical source systems: Imaging modalities, AI-augmented viewers, and reporting systems (RIS) are natural producers of FHIR Document Bundles but are typically not document management systems. Expecting these systems to correctly populate DocumentReference metadata (including EEHRxF-specific ValueSets such as eehrxf-document-type-medical-imaging-vs) places unnecessary burden on clinical source systems. ITI-106 allows them to simply POST the authoritative Bundle and let the infrastructure handle metadata extraction — analogous to how DICOM modalities send objects to a PACS without assembling the query/retrieve metadata themselves.

	- Forward compatibility across content phases: As imaging reports evolve from narrative-only (HL7 EU Imaging Level 4.2) to fully structured (Level 4.3, with coded Observations and Key Images), the Bundle structure changes significantly. With ITI-106, the client code remains stable — POST the Bundle — while the server adapts its metadata extraction logic. With ITI-105, every content phase change requires client-side updates to DocumentReference assembly.

	- Transaction is stable in IHE MHD: ITI-106 is already a defined, tested transaction in [IHE MHD|vscode-file://vscode-app/Applications/Visual%20Studio%20Code.app/Contents/Resources/app/out/vs/code/electron-browser/workbench/workbench.html] with clear semantics. Its absence from the EU Health Data API ballot appears to be a gap rather than a deliberate exclusion.

Proposed change: Add ITI-106 (Generate Metadata) as a transaction supported by the Document Access Provider actor, with conformance expectation SHALL (or at minimum SHOULD). Document Publishers SHOULD prefer ITI-106 when supported by the Access Provider, falling back to ITI-105 otherwise.

Impact if not addressed: Clinical source systems will need to implement more complex metadata assembly logic (ITI-105), increasing development effort and the risk of non-conformant DocumentReference resources in the EHDS ecosystem. This particularly affects smaller vendors and open-source projects that cannot invest in full document management capabilities.
