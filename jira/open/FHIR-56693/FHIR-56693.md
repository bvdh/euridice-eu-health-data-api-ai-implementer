# FHIR-56693: Document Exchange needs a better use of both Document Category and Document Type.

## Description

Document Exchange needs a better use of both Document Category and Document Type.

The support of MHD as proposed makes sense, however:

	- The document search proposed in the use of the MHD Document Reference resource is too primitive as it relies only on two mandatory parameters: documentType limited to the EHDS Data Category (encoded by a value set of 6 arbitrarily picked LOINC Code) and document contentType (MIME Type).

	- It is critical for the document consumer to receive in the query response with matching entries, a detailed document type as expected by the LOINC Document Type. LOINC offers a rich and precise value set, with a choice from 50 to 500 values for each EHDS Data Category.

	- The current use of Document Type is improper. It should not be hijacked to indicate a high-level business EHDS Data Category.  The choice of Value Set could be the 6 arbitrarily picked LOINC Code, as proposed, or the even more generic XDS Value Set for Document Class (allowing to extend this value set).

	- Both a clinically precise LOINC Document Type and a coarse grain Document Category are needed as they serve two different purposes. The first one to select clinically relevant documents using the query returned parameters by the requesting clinician before retrieving them.  The second one is a query request search parameters that performs a broad initial search using a server side filtering.

 

Proposed resolution :

It is proposed to update the Document Category aligned with the proposed list of LOINC document codes, where one code is assigned to each EHDS Data Category (these were the codes bound to Doc Type, the binding was incorrect, but the value set is acceptable (Note: using the XDS Document Class is a more sophisticated solution, but seems too hard for most folks to understand).

The Document Type value set should be updated to support the entire LOINC document type value set, thus offering to the clinician that creates a document the ability to use a precise and well suited LOINC Code.  If desired a Data Category related FHIR content IG, may identify a possible list of relevant codes.  But this list shall remain extensible to account for various medical practices and their future evolutions.

When such a document type code is returned associated to the query parameters matching document references, it allows the user in the document consumer to decide or not to retrieve the corresponding documents/reports, if found relevant.

Update : Search Strategy:

	- Category: This IG does not constrain category. The Category Value Set shall be defined by the EU Health API. Usage is determined by content IGs and implementation needs.  See [Document Exchange](https://hl7.eu/fhir/health-data-api/1.0.0-ballot/en/document-exchange.html) for category codes per EHDS priority category.

	- Type: Search by filtering in a query request on the server side by LOINC document type may be possible for precise document discovery, if applicable. This appears a brittle approach given the level of precision and different interpretation in different care delivery environments. However, selection by the query requester (client side selection) that is offered a precise document type returned in each matching document reference, is an effective way to decide or not to retrieve a document based on its relevance.
