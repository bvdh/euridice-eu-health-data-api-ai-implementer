# FHIR-56689: Textual clarifications

## Description

Several clarifications of a textual nature appear necessary to improve understanding of the implementation guide for the reader. The various elements that need to be adjusted are listed below.

	- Within the Document Exchange page (3.4), the order of the various sections should be adjusted for greater clarification. The sections on the consumption workflow are presented before those on the publication workflow. Switching these two elements would make the content easier for readers to understand.

	- The Resource Access page includes a “Scopes” section (3.5.8) listing FHIR resource scopes, but it does not provide any associated explanation or context. While the listed scopes are clear, the absence of a description makes it difficult to understand their intended usage, access model, or authorization expectations. It would be helpful to add a short explanation of the scope model and how these scopes are expected to be applied in the system.

	- Section 3.5.12 refers to the IHE QEDm profile. However, no link to the profile’s content is provided. Including a link to the QEDm profile would help readers to better understand this section.

	- In the Artifacts Summary page (6), the ConceptMap appears within the examples section (6.0.32), which makes it somewhat easy to miss. This is not an ideal placement given its importance, as it is referenced in other parts of the specification. It would be clearer to surface the ConceptMap in a dedicated section rather than embedding it among examples.

	- The implementation guide does not include an explanation of what mustSupport means for different types of implementations, particularly in the EEHRxF MHD DocumentReference Profile (6.14.1). Providing this clarification would help ensure consistent interpretation and implementation across systems.

	- The IHE/HL7 profiles mentioned in « Specification » sections are not introduced enough for a novice user, as each page of functional requirements (3) has a different format.

Proposed resolution :

Revision of the content of the implementation guide according to the points mentioned above to improve its clarity.

Implementation detail. Persuasive with Modification.

1. Section order — Persuasive with Mod. The prerequisite for document consumption is that content is created, not necessarily that it's published; we want to cover both the pattern that document creation is co-located with Document Access Provider (one example: [FHIR-56645 - Support On-Demand Documents](https://jira.hl7.org/browse/FHIR-56645)) or created in another system and submitted via Publication flow. Propose (A) a note explaining this distinction in Document Exchange as suggested and (B) Expand on this Content vs. Exchange distinction as it is critical to the reader understanding this IG; for example an expansion this content [Regulatory Anchors](https://hl7.eu/fhir/health-data-api/1.0.0-ballot/en/regulatoryAnchors.html#content-vs-exchange) into its own page under background, or a note in the home page.

2. Scopes — Persuasive. Bundle with [FHIR-56639](https://jira.hl7.org/browse/FHIR-56639) and [FHIR-56646](https://jira.hl7.org/browse/FHIR-56646) which refer to same scope syntax. Add description: system/ = backend-services credential; .rs = read + search; user-level scopes out of scope. Link: [SMART Scopes and Launch Context](https://hl7.org/fhir/smart-app-launch/scopes-and-launch-context.html).

3. QEDm link — Persuasive with Mod - Remove QEDm Link; IPA is the group's preferred reference; QEDm will be removed per [FHIR-56635](https://jira.hl7.org/browse/FHIR-56635);

4. ConceptMap placement — Deferred to [FHIR-56632](https://jira.hl7.org/browse/FHIR-56632) / [FHIR-56857](https://jira.hl7.org/browse/FHIR-56857) (category/type framing). The concept map approach will be revisited given Jira feedback; if we keep it we will adopt your suggestion to make it more prominent.

5. mustSupport explanation — Persuasive. [FHIR](https://hl7.org/fhir/R4/conformance-rules.html#mustSupport) requires profiles to define what must support means in context; and we should do so in the context of the IG. Profile in current state inherits 14 MS flags from IHE MHD Minimal, and thus we inherit their must support meaning. Add sentence to DocumentReference describing that we inherit the [MHD Must Support Definition](https://profiles.ihe.net/ITI/MHD/index.html#must-support). Roughly: For cardinality 0..* Must Support = Populate if Known; 1..1= consumers should handle without error.

	- Note: As you noticed in [FHIR-56688](https://jira.hl7.org/browse/FHIR-56688) the current IG should correspond the MHD DocRef profiles to their intended transactions in MHD, and the MS applies to actors participating in a transaction context. We will resolve the DocRef Profile <> Transaction consistency in that ticket.
